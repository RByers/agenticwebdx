## Principle Summary

W3C TAG §5.3 ("Don't expose garbage collection") states that JavaScript Web APIs must not allow web authors to observe when garbage collection occurs. Because GC algorithms and timing vary across user agents and evolve as browsers optimize performance, exposing GC timing causes web applications to behave inconsistently across environments, forces authors to write defensive workarounds, and constrains browser engines from changing their GC strategies lest existing sites break.

In practice, this means regular Web APIs must have predictable object and data lifetimes and must not behave like implicit weak references (for example, a property that turns `null` after GC runs, or `getElementsByTagName` inconsistently reusing vs. recreating an `HTMLCollection` depending on whether the previous wrapper was collected). When weak-reference behavior is genuinely needed, it belongs in dedicated primitives like `WeakRef` and `FinalizationRegistry` that explicitly signal GC interaction to the author.

## Fit for Coding Agents

This principle aligns well with AI coding agents (`agent_fit: good`) because coding agents depend heavily on local invariants in the token context and on fast, deterministic test-runner feedback loops to validate their output. When an agent verifies generated code, it typically executes short-lived unit tests or headless browser scripts (such as Playwright or Vitest) under minimal memory pressure. In those brief, clean execution environments, garbage collection rarely runs at the exact boundary between two statements. If a Web API's observable behavior depends on GC timing—such as returning the same `HTMLCollection` from `getElementsByTagName` only if the previous wrapper has not yet been collected, or nulling out an implicit weak property—the agent's automated verification loop will pass 100% of the time while shipping intermittent "heisenbugs" that only manifest under real production memory pressure or in different browser engines.

Furthermore, LLMs reason about code using standard JavaScript reference priors learned across massive corpora: object properties remain populated unless explicitly mutated, and accessor/query methods either consistently return a cached reference or consistently allocate a new object. Hidden GC-dependent state transitions violate these local reasoning priors and fail silently or far from the root cause without actionable stack traces, which is one of the hardest failure modes for an agent to debug iteratively.

By contrast, isolating GC-sensitive semantics to explicit primitives like `WeakRef` and `FinalizationRegistry` surfaces the lifetime hazard directly in the local token stream. When `WeakRef.prototype.deref()` appears in context, both the model's training priors and TypeScript's type system (`T | undefined`) force the agent to handle the collected case explicitly rather than being surprised by hidden wrapper collection in a DOM API.

## Value as a Slide Example

While §5.3 helps coding agents avoid non-deterministic lifetime bugs, it is not a strong standalone slide example for the TPAC breakout (`slide_example: neither`, `example_strength: 2`). The rule is primarily a foundational browser-engine and cross-browser interoperability invariant designed to prevent Hyrum's Law from locking engines into specific GC strategies, and spec authors already universally agree that ordinary Web APIs should not leak GC timing (unlike legacy quirks in `getElementsByTagName`).

The one genuinely interesting agent-specific insight is that **short-lived headless browser test loops used by agents almost never trigger GC**, meaning any GC-timing sensitivity in a Web API will systematically evade an agent's self-verification harness. That makes it a useful minor supporting point inside a broader slide on *Determinism in the Agent Verification Loop*, rather than a headline example of how web standards need to adapt for agent DX.
