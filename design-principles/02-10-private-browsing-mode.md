# §2.10 Consider how your API should behave in private browsing mode

## Principle Summary

W3C TAG Design Principle §2.10 instructs specification authors to define how their APIs behave when a user is in private browsing mode so that user privacy guarantees are preserved. Specifically, it highlights three core obligations: mitigating any API surface that would allow a site to correlate a single user's activity across normal and private browsing sessions (for example, by introducing noise), ensuring that client-side storage APIs do not persist data on the device after the private browsing session ends (without exposing detectable API differences to the site), and isolating simultaneous normal and private sessions on the same origin so that state changes or cross-window events like the `storage` event never leak across the session boundary.

This principle exists to protect end users from cross-session tracking and local device traces when they opt into private browsing. Rather than changing how web developers call APIs, it governs how browsers partition underlying storage, events, and hardware/identity signals behind the scenes.

## Fit for Coding Agents

This principle is neutral (orthogonal) with respect to AI coding agents because it governs browser-enforced privacy boundaries and internal specification mechanics rather than developer-facing API ergonomics. Protecting an end user from having their private and normal browsing sessions correlated, or from having private-session data written permanently to disk, is a browser security and privacy invariant that applies identically regardless of whether the website's JavaScript was authored by a human developer or generated by an LLM.

To the limited extent that this principle touches application code, its requirement that private browsing storage behave as an isolated, ephemeral partition without revealing detectable API differences (reinforcing §2.9) is quietly helpful to coding agents. Because modern browsers provide working, in-memory implementations of `localStorage`, `IndexedDB`, and Cache Storage in private windows and simply isolate `storage` events to the private session rather than disabling the APIs or requiring special mode checks, LLM-generated code can use standard storage patterns without hallucinating or maintaining brittle "private mode" fallback branches. Even where an API introduces privacy noise to prevent cross-session correlation, that noise is designed to defeat fingerprinting rather than alter normal application control flow.

## Value as a Slide Example

This principle is neither a "clearly-useful" nor a "clearly-harmful" slide example for a TPAC session on how web standards should adapt to AI coding agents (1/5 strength). It is fundamentally a privacy self-review checklist item for specification authors—ensuring ephemeral storage cleanup, cross-session partitioning of events like `window`'s `storage` event, and anti-correlation mitigations—not a developer-experience trade-off.

Featuring §2.10 on a slide about Agentic DX would distract from the core thesis of the session, as no one would argue that private browsing isolation should change because agents are writing code, nor does this principle illustrate any friction between human-oriented API ergonomics and LLM capabilities.
