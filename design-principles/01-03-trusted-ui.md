## Principle Summary

W3C TAG Design Principle §1.3 ("Trusted user interface should be trustworthy") directs web platform designers to ensure that new web features do not allow untrusted web pages to mimic, obscure, or spoof trusted browser user interfaces—such as the address bar, security indicators, and permission prompts. End users depend on these browser-controlled surfaces to verify the identity of the site they are interacting with and the permissions they are granting.

When a web feature blurs the line between untrusted page content and trusted browser chrome, it undermines the user's ability to judge what information is genuine. The principle cites `window.alert()` as a classic cautionary example: because it lets untrusted page script summon a modal dialog that looks like part of the browser itself, it is frequently abused by scam websites to trick users, and likely would not be approved if proposed today.

## Fit for Coding Agents

This principle is fundamentally neutral with respect to AI coding agents because it governs the security boundary between the user agent (browser chrome) and untrusted web content to protect end users, rather than optimizing for developer ergonomics. A phishing page, UI redressing attack, or spoofed permission prompt is equally dangerous to the end user whether its HTML, CSS, and JavaScript were authored by a human developer or generated by an LLM. Consequently, the transition from human-written to agent-written code does not alter the need to keep trusted browser UI visually and functionally distinct from page content.

At the margins, there are two minor secondary interactions with coding agents. First, legacy APIs that violate this principle—most notably `window.alert()`, `confirm()`, and `prompt()`—are heavily overrepresented in LLM training data from decades of tutorials and quick demos. Coding agents frequently reach for `alert()` as a low-ceremony placeholder, which then backfires in the agentic verification loop because synchronous browser-chrome modals freeze page execution and hang headless browser automation (e.g., Playwright or Puppeteer) unless explicit dialog listeners are configured. In contrast, modern in-page primitives like `<dialog>` and the Popover API clearly belong to page content and remain directly inspectable and clickable in the DOM during automated testing. Second, when newer APIs enforce trusted-UI protections—such as restricting CSS properties on the `<permission>` element or clamping popup window coordinates so they cannot overlap the address bar—coding agents may hallucinate standard CSS styling or positioning that fails silently unless the browser emits explicit console or DevTools warnings into the agent's feedback loop.

## Value as a Slide Example

This principle is not useful as a standalone slide example (`1/5`, `neither`) for a TPAC session on how web standards should adapt to coding agents redefining DX. Because the rule is about preventing untrusted websites from spoofing browser chrome (like the address bar or permission prompts) to deceive end users, standards participants will rightly view it as a permanent end-user security invariant rather than a developer-experience trade-off affected by AI code generation.

If mentioned at all, it only belongs in a brief introductory grouping noting that core end-user security, privacy, and trust boundaries apply equally regardless of whether a human or an agent wrote the site. While the contrast between `window.alert()` (which mimics browser UI and blocks headless test runners) and `<dialog>` (which stays in the DOM) is a mildly interesting footnote, other principles directly addressing API ergonomics, error observability, and legacy footguns make far stronger slide examples.
