# §2.11 Don’t reveal that assistive technologies are being used

## Principle Summary

W3C TAG Design Principle §2.11 ("Don’t reveal that assistive technologies are being used") states that Web APIs must not allow websites to detect whether a user is employing assistive technology (AT) such as a screen reader or switch device. Because AT usage reveals sensitive personal and medical information about vulnerable users, exposing it to web origins enables fingerprinting, surveillance, or discriminatory denial of access, violating §1.2 ("It should be safe to visit a web page").

Even well-intentioned accessibility proposals must be redesigned if they leak AT usage as a side effect. For example, early drafts of the Accessibility Object Model (AOM) defined dedicated events that fired only when assistive technology interacted with an element; AOM subsequently removed those events and replaced them with standard synthetic DOM events so that AT interactions remain indistinguishable from regular user input.

## Fit for Coding Agents

In its primary motivation, §2.11 is orthogonal (`neutral`) to AI coding agents: it is a fundamental end-user privacy, security, and anti-discrimination boundary that protects users with disabilities from origins regardless of whether the site's code was written by a human or an LLM. Because coding agents lower the cost of generating telemetry and fingerprinting scripts, enforcing strict privacy boundaries at the browser API level remains strictly necessary.

However, the API design pattern this principle enforces—illustrated by the Accessibility Object Model (AOM) replacing AT-specific events with standard synthetic DOM events—has a positive secondary effect on coding agents. LLMs have massive training priors for standard DOM events (`click`, `input`, `focus`) and rarely remember to attach parallel, AT-only event listeners unless explicitly instructed. By folding assistive technology actions into standard synthetic DOM events, code generated by an agent for the default happy path works across assistive technologies without extra token overhead, dual event handlers, or niche API hallucinations.

Furthermore, withholding AT detection prevents coding agents from taking a harmful shortcut when asked to fix accessibility issues: branching on a hypothetical screen-reader flag to serve a separate, second-class fallback DOM rather than authoring semantic HTML and proper ARIA state. It also aligns cleanly with the feedback loop of modern coding agents, which frequently inspect the accessibility tree and trigger synthetic actions in headless browsers (via Playwright or WebDriver BiDi) to verify their own UI changes.

## Value as a Slide Example

§2.11 is a poor fit as a headline slide (`neither`, 2/5) for a TPAC session on how web standards should adapt to coding agents because its core purpose is end-user privacy and anti-discrimination rather than developer ergonomics. Standards bodies will not (and should not) change user-privacy boundaries because of AI coding agents.

Its only value on a slide is as a brief supporting example of how unified, modality-agnostic primitives help both privacy and agent reliability: when AOM replaced AT-specific events with standard synthetic DOM events (`click`, `input`), it eliminated a parallel event surface that coding agents would otherwise frequently forget to implement or fail to test in standard browser automation loops.
