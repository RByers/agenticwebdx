Should we design for agents?

  • Topic 1 of 7. Proposal text: “Should we take agent consumers into account at all? The counterarguments are that agents are not uniform — what is efficient for one model generation may not be for the next — and the landscape is still volatile, whereas Web APIs are permanent.”

Agents churn. Web APIs don't.

Moves in months

  • ≥10× cheaper per year for the same capability level

Holds across generations

  • 24 yrs mutation events: in spec 2000, removed from Chrome 2024

Design for today's agents, or only for what holds across generations?

Sources: a16z; Epoch AI; Chrome for Developers.

Details: analysis/volatility.md

  • Skeptic's case: models turn over yearly, APIs last decades
  • Left (moves in months): same capability gets ≥10× cheaper/year
  • Right (holds across generations): APIs live 24+ years (mutation events), so a new API is used mostly by models that don't exist yet
  • Ask: should agent DX shape only properties that held across every generation?

Most TAG principles hold for agents

  • 3 vs 5 tokens: requestAnimationFrame vs RTCDTMFSender — common words (§12.1) beat abbreviations
  • 15 vs 9 tokens: {bubbles: true, cancelable: false} vs true, false (§6.5)

No TAG principle mentions AI. What about the guidelines that assume a human author?

Sources: W3C TAG Web Platform Design Principles (103-principle audit); Anthropic (Sep 2025); Jain et al., ICSE 2025; o200k_base.

Details: analysis/design-principles.md; per-principle files in design-principles/

  • Evaluated all 103 TAG principles one at a time: 45 help agents, 48 neutral, 10 pull against
  • The TAG doc never mentions AI; no TAG issue on coding agents as consumers
  • Anthropic, OpenAI: tools ergonomic for agents are also intuitive for humans
  • Consistency: for models it is the prediction mechanism (rare APIs: 61% invalid calls vs. 6% common)
  • Dictionaries and string enums: ~1.6× tokens, but self-describing calls, no boolean trap
  • Debuggability and common words: introspectable APIs let agents check without screenshots; abbreviations tokenize badly

Textual formats for humans (TAG §2.7)

What §2.7 & §11.1 say

  • SVG path “designed to be compact… cost to human readability has remained”
  • JSON no comments or trailing commas, mandatory key quotes → “prone to syntactic errors”
  • CSS ignores property typos (§2.7); forgiving markup gives a “shallower learning curve” (§11.1)

Why it flips for agents

  • 8 vs 16 tokens: M10 10 L20 20 vs moveTo(10,10) lineTo(20,20)
  • 99.9% of AI code passes syntax checks; strict JSON schemas enable constrained decoding
  • 0 errors when CSS drops a typo — forgiving parsers blind text-native machines in the loop

Agents don't need forgiving syntax — they need machine-checkable diagnostics.

Sources: W3C TAG §2.7 & §11.1; Veracode (2026); Mündler et al., PLDI 2025; o200k_base.

Details: design-principles/02-07-text-formats.md, design-principles/11-01-requirements-on-authors-and-implementers.md

  • Only principle titled “for humans”; assumes machines would use binary
  • Agents are machines whose native interface is text
  • JSON strictness was a human pain; for agents syntax is solved (99.9%) and strictness helps
  • Forgiving CSS/HTML turns a one-turn fix into a silent bug
  • Compact syntax (SVG paths) is cheaper in tokens (8 vs. 16); no Brotli in a context window
  • Nuance: unlabeled flags in microsyntaxes (SVG arcs) do cause errors

Usability over third-party tools (TAG §2.15)

What §2.15 says

  • Outlive “Web platform features last a lot longer than most third-party tools” that prototype them
  • Override avoiding tool clashes is “rarely an acceptable tradeoff” if it hurts native syntax
  • Rare Array.includes() (PrototypeJS) and Grid [line-name] (Sass) treated as exceptions

Why it fails for agents

  • Weights popular tools (Sass, Babel/TS, React, Tailwind) are permanently baked into model priors
  • Clashes CSS Nesting & vs Sass &__child; Stage 3 vs legacy TS @decorator
  • +20% issues solved when linters/compilers gate edits — breaking tools breaks the agent loop

Under §2.15, coding agents are “third-party tools” — yet they write the code.

Sources: W3C TAG §2.15 & §1.1; Yang et al., NeurIPS 2024 (SWE-agent); Amplifying (2026).

Details: design-principles/02-15-third-party-tools.md, design-principles/01-01-priority-of-constituencies.md

  • §2.15: favour native syntax over tools because tools come and go
  • Tools don't go away: they're fossilized in model weights
  • Same sigil, different meaning confuses models: Sass vs. native &, TS vs. TC39 decorators
  • Tools (tsc, ESLint, bundlers) are the agent's feedback loop; if they reject native syntax, the agent strips it
  • Ask: are agents “authors” or “third-party tools” in the priority of constituencies?

Leave the web better (TAG §1.9)

What §1.9 & §1.8 say

  • Break “consistency with existing problematic design patterns is not a good reason to propagate” them
  • Replace prefer clean-sheet APIs over extending defective legacy features (§1.9)
  • Keep old never remove legacy APIs — unless used “only in test cases or examples” (§1.8)

Why it backfires for agents

  • Traps MutationObserver takes options in observe(); IntersectionObserver in new
  • 70–90% of completions in older files pick the deprecated API over its clean-sheet replacement
  • Examples breaking patterns seen “only in test cases or examples” (§1.8) breaks what LLMs trained on

When old APIs never die, fixing a flaw only in the new one sets a statistical trap.

Sources: W3C TAG §1.9, §1.8 & §7.10; Wang et al., ICSE 2025.

Details: design-principles/01-09-leave-the-web-better.md, design-principles/01-08-removing-features.md

  • §1.9: don't copy flawed patterns; §1.8: old APIs almost never removed
  • Near-miss siblings: io.observe(el, {threshold}) silently ignored; live vs. static NodeList
  • Legacy APIs dominate training data: deprecated API chosen 70–90% when surrounding code is old
  • “Only in examples” usage is what models train on, so they resurrect it

Token efficiency

  • What makes a Web API token-efficient?
  • For writing code against it
  • For reading code that uses it
  • Topic 4 of 7. Proposal text: “What makes a Web API token-efficient, both when writing code against it and when reading code that uses it?”

Ceremony costs tokens. Long names don't.

Same taskOlder patternNewer pattern

  • 1 vs 4 tokens: .getElementsByClassName vs popovertarget
  • 1.4× vs 2.6× OCaml vs Python: final code vs total agent output
  • 5× output vs input token price, yet re-read input dominates agent cost

Token counts: own measurement, o200k_base tokenizer, hand-written equivalent snippets. Wu, Anderson & Guha, arXiv:2607.22807; Bai et al., arXiv:2604.22750; Anthropic pricing (Claude Sonnet 5.5).

Details: analysis/token-efficiency.md

  • Ceremony costs tokens, not long names
  • Newer APIs that pave a pattern cut tokens ~2–6× (median 2.2× over 9 pairs; o200k tokenizer)
  • Web component counter: vanilla 123 tokens, Lit 88, React 61, Svelte 29
  • Cheapest is sometimes the unsafe one (innerHTML +=)
  • Familiar names are cheap: tokenizers learned from existing code
  • Unfamiliarity costs more: OCaml vs. Python 2.6× total output, mostly error recovery
  • Input (re-reading code) dominates agent cost, so verbose code is paid every turn
  • Ask: should new APIs look like what agents already write, even if not the cleanest?

Robustness

  • What makes a Web API robust for agents?
  • i.e. harder to misuse
  • Topic 5 of 7. Proposal text: “What makes a Web API robust for agents, i.e. harder to misuse?”

Agents only fix what fails loudly

Silent failures persist

  • 85% of XSS-prone tasks left exploitable by AI-written code
  • 61% of GPT-4o calls to rare APIs invalid, vs. 6% to common ones
  • 70–90% deprecated-API use when surrounding code is old (9–18% if modern)

Loud failures get fixed

  • 99.9% of the same AI-written code passes syntax checks
  • 94% of LLM TypeScript compile errors are type errors; type-checked decoding cuts them 52–75%
  • +20% issues solved when a linter rejects the agent's broken edits (15% → 18%)

CSS drops display: flexbox silently. How should an API that can't throw say so?

Sources: Veracode, 2026 GenAI Code Security Report; Jain et al., ICSE 2025 (CloudAPIBench); Wang et al., ICSE 2025; Mündler et al., PLDI 2025; Yang et al., NeurIPS 2024 (SWE-agent).

Details: analysis/robustness.md

  • Mistakes that get reported (syntax, types, lint) get fixed in the loop
  • What survives: insecure but working code, plausible calls to rare APIs, legacy APIs
  • Veracode: syntax 99.9% pass, security 56%, XSS 15%, SQL injection 83%
  • Interpretation: SQLi's idiomatic API is also safe; XSS needs remembering → case for setHTML(), Trusted Types
  • Rare APIs: GPT-4o 61% invalid calls vs. 6% for common ones
  • Types catch errors: 94% of TS compile errors are type errors; lint feedback +20% issues resolved
  • Web is full of silent failures: CSS drops bad declarations, nothing reaches the console
  • Levers: console warnings, readable reporting channel, dictionaries, precise WebIDL, safe defaults

Evaluation

  • Unfamiliar APIs cost extra tokens (lookup, trial and error)
  • Better designs score worse until training data catches up
  • How do we separate familiar from better?
  • How do we evaluate with such a delayed feedback loop?
  • Topic 7 of 7. Proposal text: “An API’s token cost is not an intrinsic property. An agent implementing an unfamiliar API spends tokens on lookup, trial and error, and correction, so a design that would be more token-efficient at parity of familiarity measures as worse until training data catches up — which takes years. Any evaluation we run today privileges familiar over better. How do we separate the two, and how do we evaluate API designs, or design principles, given such a delayed feedback loop?”

Is the framework now the platform agents target?

Sources: Amplifying, What Claude Code Actually Chooses (Feb 2026); Lovable docs; v0 FAQ; npm registry download API.

Details: analysis/what-agents-write.md; data: npm-downloads.csv

  • Agents converge on React + Tailwind + shadcn/ui + lucide
  • Claude Code picks: shadcn/ui 90%, Tailwind 68%; v0 and Lovable offer no framework choice
  • npm Sep 2024 → Sep 2026: lucide 61×, shadcn 53×, Tailwind 12×, React 6.8× vs. lodash baseline 3.2×
  • All of npm inflated (agents spin up projects), hence the baseline
  • Radix Dialog and Floating UI are JS stand-ins for <dialog>/popover and anchor positioning
  • Native feature under-use: plausible but unmeasured; only Chrome's own eval (+37 pts with guidance)
  • Counterpoint: newer models do pick newer tools (Prisma → Drizzle)
  • Ask: freeze, or “the framework is the platform” (get native features into the defaults)?

Evals reward the familiar

  • 1.3–1.7× tokens in OCaml vs. Python on the same tasks, mostly fixing failed attempts
  • 25–38% of completions choose a deprecated API over its replacement
  • 53% → 100% pass rate on Next.js 16 APIs absent from training data, once docs are in context

So how do we evaluate a design that is better, but new?

Sources: Liang et al., RustEvo² (2025); Wu, Anderson & Guha (2026); Wang et al., ICSE 2025; Vercel (Jan 2026).

Details: analysis/evaluation.md

  • Measured cost mixes design quality with how much the model has seen
  • RustEvo²: pass rate 56% on pre-cutoff APIs vs. 33% post-cutoff
  • OCaml vs. Python: same-size solutions, 1.3–1.7× tokens; penalty shows as cost, not failure
  • Deprecated APIs chosen 25–38% of the time
  • Docs in context help (Vercel 53% → 100%) but aren't free
  • Cleanest familiarity-only test: renamed pandas/NumPy, pass rate 19% → 1.5%
  • Ideas: docs in context for both designs, fresh or renamed APIs, report tokens and turns, re-run each model generation
  • Ask: how do we evaluate a design that's better but new?

Field notes from 329 agent sessions

Two device-heavy web apps, built almost entirely by coding agents

Details: analysis/agent-sessions.md; data: patterns, incidents

  • First-hand: 329 Claude Code sessions, two hobby apps, Jul–Oct 2026
  • zpcrweb (WebUSB, File System Access, IndexedDB); meshcore-web (PWA, Web Bluetooth, Web Serial)
  • Subagents read every transcript: 167 incidents, 14 recurring patterns
  • Caveat: one developer, one agent; LLM-assisted counts; token figures are lower bounds

“It's a pre-existing flake”

  • 70 of 311 sessions hit a flaky browser test
  • 49 of them moved on without finding the cause
  • 10 sessions waved off the same dialog race
  • ~10 h of agent time lost to flakes

The usual cause: browser state with no observable “done”, such as an IndexedDB commit, a render, a hash navigation or a popover opening. Tests sleep, then flake.

“I said the Cq-filter test flakiness was pre-existing. It wasn't — it was mine. The check I added yesterday left its run in IndexedDB…”

Should async platform state always expose a completion signal agents can wait on?

Source: our own Claude Code sessions, Jul–Oct 2026 (see notes). Pattern P6 in agent-session-patterns.csv.

Details: agent-sessions.md, example 1

  • 83 episodes in 70 sessions; agent called it “flaky”/“pre-existing” without root cause in 49
  • ~10 h total; worst: 51 min, 117 tool calls, then “environmental”
  • Causes: popstate/hashchange fire separately, IndexedDB flush with nothing to await, dialog/popover not yet rendered
  • IndexedDB state leaking between tests
  • Caveat: many are app bugs; platform question: why is “wait until done” so hard to express?

Vague errors breed unreliable hacks

  • 4sessions hit WebUSB's A transfer error has occurred. The agent guessed “stalled endpoint” and added retries; the eventual fix sorts errors by regex over the message.
  • 1Web Bluetooth User cancelled the requestDevice() chooser, when nothing was advertising and nobody cancelled.
  • 3wrong theories in a row about whether getDevices() needs a flag. The wrong one went into the README and test names.
  • 7 of 13 opaque-error diagnoses wrong or never confirmed
  • ~490 tool calls spent on them

Should errors carry machine-readable causes, and flag and permission state be queryable?

Source: our own Claude Code sessions, Jul–Oct 2026 (see notes). Patterns P1, P2 and P12.

Details: analysis/agent-sessions.md, examples 2, 4, 5

  • WebUSB: generic NetworkError for unplug, stall and cancel; agent guessed wrong, final fix regex-matches messages
  • Web Bluetooth: empty chooser reported as “User cancelled”
  • getDevices(): agent relied on stale 2020 info; three wrong theories, ~110 tool calls
  • 13 opaque-error episodes: first guess right in only 5

Can't automate it? Fake it.

  • 15sessions hit an API that automation can't drive: the WebUSB and Bluetooth choosers, the folder picker, permission lapse, page visibility
  • 450+lines of permanent fakes: a recorded navigator.usb, a mock Bluetooth radio, an OPFS stand-in for the folder picker
  • 11episodes, ~2 h: saved folder permission silently lapses on reload; the agent's headless probe never reloaded, so “confirmed” it persists
  • 6 ssleep: typing via CDP grants user activation, so requestDevice() opened a chooser and hung

Fakes encoded wrong beliefs, so tests passed. Should every gated API ship with a testing hook?

Source: our own Claude Code sessions, Jul–Oct 2026 (see notes). Patterns P3 and P4.

Details: analysis/agent-sessions.md, examples 6, 7

  • 15 episodes: device pickers and permissions can't be automated
  • Agents built fakes: navigator.usb replay, mock Bluetooth radio, picker stand-ins
  • Some fakes encoded the wrong permission model → tests passed on false beliefs
  • File System Access permissions after reload: ~2–2.5 h of confusion
  • CDP typing counted as user activation → chooser hang in headless Chrome

Can't see it, can't use it: rebuild it

Layout is invisible

  • 24/24 CSS bugs found by the user, not the agent
  • 11/14 of those had been “verified” by screenshot or test

Gaps get reimplemented

  • 728 lines of PNG rasterizer and pixel font, instead of the browser
  • 3 IndexedDB schema redesigns: no partial update

Agents go to extreme lengths to route around the platform. Which gaps should we close?

Source: our own Claude Code sessions, Jul–Oct 2026 (see notes). Patterns P8, P9 and P10.

Details: analysis/agent-sessions.md, examples 9, 11–13

  • Layout: agent missed all 24 CSS bugs the user reported; 11 of 14 had been “verified” by screenshot
  • Silent failure: invalid min(1fr, 19px) dropped the whole grid template
  • Agents reimplemented the platform: ~300 lines of crypto, 728-line PNG rasterizer
  • ~1,900 lines hand-written, ~800 later deleted
  • Caveat: partly agent judgement; in 3 cases it avoided existing features over cross-browser worries

Mobile: only the human can see it

  • 4/4 mobile and installed-app bugs found by the user on a real phone
  • 0 sessions where the agent turned on touch or mobile emulation
  • 7 min until the first fix was re-reported

The cases: 100dvh under Chrome's collapsing URL bar, the on-screen keyboard shrinking the layout, missing safe-area insets, and no maskable icon. With no portable signal for “the keyboard is up”, the agent used “a text field has focus”.

“Typecheck is clean and all tests pass (1399 core, 262 web). I haven't tried it on an Android phone, so that's the thing to check by hand.”
