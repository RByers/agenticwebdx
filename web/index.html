Agents are redefining DX.
[How] should web standards adapt?

Lea Verou & Rick Byers

The Web Platform's design principles implicitly assume a human developer as the primary API consumer. As a growing share of web code is written by agents, these assumptions stop holding uniformly, and some pull in opposite directions.

Goal: make progress on the session's questions and identify people interested in exploring this further.

The shift is well under way

Web development is moving from human-led to agent-led. How far?

Full analysis, data and open threads: analysis/the-shift.md.

Standards, docs and APIs were designed for a human reading MDN. Agents are now a major consumer too; whether they become the typical one is still open.

Source: botcommits.dev (GH Archive + GitHub commit search; data). Counts only commits that carry an AI attribution, so a lower bound.

Full analysis, data and open threads: analysis/the-shift.md.

botcommits.dev (data updated 18 Aug 2026; data.json, code and raw queries) counts public commits carrying an AI attribution (Claude Code's Co-Authored-By trailer, bot authors for Copilot coding agent, Jules, Devin, etc.) and divides by monthly GH Archive push events. The six tracked tools went from ~2% of push events in Dec 2025 to 15.1% in Apr 2026, then 16.0%, 18.6% and 17.8% in May–Jul. Claude Code is ~99% of the attributed commits (19.8M in Jul 2026).

This tells a more cautious story than the docs and survey data. Month-on-month growth in Claude Code commits fell from +89% (March) to +14% (July); the March forecast of exponential growth predicted ~98M commits for July versus ~20M actual. Logistic and Gompertz fits now beat the exponential, with an inflection around April 2026 and a ceiling of roughly 22–30M Claude commits per month (wider across fit configurations).

Caveats, from the site: it measures attribution markers, not AI use. Cursor and Copilot inline completions add no marker; squash merges collapse many agent commits into one; GitHub reports 81.5% of contributions happen in private repos. The commits-per-push ratio is uncertain (≈1:1 from Octoverse totals, ≈3:1 implied by other estimates), so the 17.8% of pushes reads as roughly 6–18% of commits. A plateau in attributed commits could also be a change in attribution behaviour rather than usage.

Bridge to the discussion: if the typical “developer” reading a spec, an MDN page or an error message is increasingly an agent, which of our design principles still hold, and which pull in the opposite direction?

Design for today's agents, or only for what holds across generations?

Sources: a16z; Epoch AI; Amplifying.ai (Feb 2026); Anthropic pricing & model deprecations; Chrome for Developers; TechCrunch; Churilov, arXiv:2605.17062; Vercel (Jan 2026).

Full analysis, data and open threads: analysis/volatility.md.

The skeptic's case: models are not uniform and turn over every year, so optimizing a permanent Web API for this year's agent is optimizing for a consumer that will be retired long before the API is. The data supports the premise (left column) but suggests some agent properties are as stable as the web itself (right column), and that the cheap-tokens argument does not hold at the frontier.

Moves in months

≥10×/year for the same capability. a16z, “Welcome to LLMflation” (Guido Appenzeller, 12 Nov 2024): “For an LLM of equivalent performance, the cost is decreasing by 10x every year.” At MMLU 42: GPT‑3 at $60/M tokens (Nov 2021) vs. Llama 3.2 3B at $0.06/M (late 2024), ~1,000× in three years; at MMLU 83 (GPT‑4 class), ~62× since March 2023. Epoch AI, “LLM inference prices have fallen rapidly but unequally across tasks” (12 Mar 2025): 9× to 900× per year depending on the benchmark threshold; GPT‑4's GPQA (PhD science) level fell 40×/year. Caveats: both rely on benchmarks that may be contaminated; Epoch notes the fastest drops were the most recent and may not persist. Related: Epoch AI (25 Jun 2025): the longest context windows grew ~30×/year since mid‑2023 (GPT‑4 8K in 2023 → Gemini 2.5 Pro 1M, Llama 4 Scout 10M in 2025).

79% → 0%. Amplifying.ai, “What Claude Code actually chooses” (Edwin Ong & Alex Vikati, Feb 2026): 2,430 open-ended prompts on real repos that never name a tool, across Sonnet 4.5, Opus 4.5 and Opus 4.6. Prisma was 79% of Sonnet 4.5's JS ORM picks and 0% of Opus 4.6's (Drizzle 100%, n=29); Celery 100% → 0% and Redis 93% → 29% for Python. Sonnet 4.5 shipped 29 Sep 2025, Opus 4.6 on 5 Feb 2026. “Custom/DIY” was the top pick in 12 of 20 categories, and a companion write-up reports that rephrasing the same requirement gave the same pick only ~76% of the time. Caveats: one vendor's models, one harness, small per-category n. This is the non-uniformity point: two consecutive generations from the same vendor disagree on defaults. I found no comparable published study across vendors (Claude vs. GPT vs. Gemini) for front-end choices.

1 year. Anthropic model deprecations page: claude-opus-4-1-20250805 retired 5 Aug 2026; Claude Sonnet 4 and Opus 4 (May 2025) retired 15 Jun 2026; Claude 3 Opus (Mar 2024) retired 5 Jan 2026; Claude 3 Haiku (Mar 2024) retired 20 Apr 2026. Retired models lived roughly 12–25 months on the first-party API. Partner clouds keep some longer.

Holds across generations

24 years. Mutation events were specified in DOM Level 2 Events (W3C Recommendation, 13 Nov 2000), deprecated in 2011, replaced by MutationObserver in 2012, and removed from Chrome 127 (stable 23 Jul 2024): 13 years from deprecation to removal. Other examples still required by the specs today: document.all (IE4 era, special-cased as [[IsHTMLDDA]] in ECMAScript), “The marquee element must implement the HTMLMarqueeElement interface”, and sync XHR, which the XHR Standard still says is “in the process of being removed from the web platform”. For scale, a pull of the chromestatus.com API on 27 Oct 2026 lists 1,894 entries “Enabled by default” vs. 198 “Removed”, and few of those are removals of whole, interoperable, standardized APIs: roughly 19 are prefixed features, 18 non-standard or legacy ones, 19 TLS or protocol changes, and many of the rest remove single members or restrict a feature to secure contexts (see analysis/volatility.md). The chromestatus status field is maintained by hand, so treat that ratio as rough. The asymmetry: with models living 1–2 years and APIs living decades, an API designed this year will be consumed mostly by models that don't exist yet.

$60 → $50. Cheap tokens are cheap only for yesterday's capability. GPT‑4 launched at $0.03/1K prompt and $0.06/1K completion tokens, i.e. $30/$60 per M (8K context; TechCrunch, 14 Mar 2023). Anthropic's current top tier, Claude Fable 5.1 (Sep 2026), is $10/$50 per M (Anthropic pricing). Input dropped 3×, output barely moved. a16z makes the same point: o1 launched at the same $60/M output price as GPT‑3. Meanwhile usage per request grows: OpenRouter/a16z “State of AI” (Dec 2025): average prompt tokens per request rose ~4× (≈1.5K → 6K+) and programming went from ~11% to over 50% of token volume during 2025. Caveats: different vendors; cache hits are much cheaper ($0.25/M on Fable 5.1); mid-tier models (Opus 5.5 $4/$20, Sonnet 5.5 $2/$10) are far cheaper. So token efficiency still matters for whoever is paying for frontier agents, and context window budget is a constraint at any price.

~5%. Churilov, “The Range Shrinks, the Threat Remains: Re-evaluating LLM Package Hallucinations on the 2026 Frontier-Model Cohort” (arXiv, May 2026, rev. Aug 2026): across 199,845 Python and JavaScript prompts, Claude Sonnet 4.6, Claude Haiku 4.5, GPT‑5.4‑mini, Gemini 2.5 Pro and DeepSeek V3.2 hallucinated packages at 4.62%–6.10%, vs. 5.2% (commercial) to 21.7% (open-source) in Spracklen et al., USENIX Security 2025 (2024 models). 127 hallucinated names were shared by all five models. Caveat: single-author preprint, not peer reviewed. Related: Twist et al., “LLMs Love Python” (2025): across 8 models, popular libraries (e.g. NumPy) were used unnecessarily in up to 48% of cases, and Wang et al. (ICSE 2025): all 7 LLMs tested used deprecated APIs, attributed to training data. Familiarity bias and training lag are structural, not generation-specific.

53% → 100%. Vercel, “AGENTS.md outperforms skills in our agent evals” (Jude Gao, 27 Jan 2026): on Next.js 16 APIs “not in current model training data” ('use cache', cacheLife(), connection(), async cookies()…), no docs 53%; a docs skill 53% (never invoked in 56% of cases) or 79% with explicit instructions; an 8KB docs index in AGENTS.md 100%. Caveats: one vendor's own eval on a narrow API set. Relevant to the “optimize docs and specs for machines, not APIs” option: every model has a training cutoff, and docs in context remove most of the penalty for a new API. That holds across generations. See the Mintlify numbers on the docs slide (10.8M /llms.txt fetches and 2M+ MCP calls in August 2026) and MDN's MCP server. I found no public data on what fraction of agent sessions include a docs lookup.

Discussion prompt: if the consumer changes every year, should agent DX only shape properties that held for every generation so far, and leave token-level tuning to models and docs? Candidates the room could test (not shown by the data above): explicit errors, consistency, fewer footguns, familiar shapes, machine-readable docs.

Token counts: own measurement, o200k_base tokenizer, hand-written equivalent snippets. Wu, Anderson & Guha, arXiv:2607.22807; Bai et al., arXiv:2604.22750; Anthropic pricing (Claude Sonnet 5.5).

Full analysis, data and open threads: analysis/token-efficiency.md.

Claim. What makes a Web API expensive in tokens is ceremony (setup objects, callbacks, lifecycle boilerplate, glue code), not long identifiers. Recent platform additions that pave a common pattern (classList, fetch, loading=lazy, AbortSignal.timeout(), Object.groupBy()) cut the tokens for the same task by about 2–6×. But for an agent the bigger cost is unfamiliarity: lookups, failed attempts and fixes. That means a new, terser API can cost more in practice than an old, verbose one until models have trained on it.

Measurement method (table and first stat). I wrote a pair of functionally equivalent snippets for each task, in one consistent style (2-space indent, single quotes, no comments). I counted tokens with OpenAI's o200k_base (GPT-4o and later) and cl100k_base (GPT-4) encodings via tiktoken 0.14.0, and with the Qwen2.5-Coder-7B-Instruct tokenizer via Hugging Face tokenizers. Claude's tokenizer is not public. Qwen's vocabulary overlaps heavily with cl100k, so it is not an independent check. All three agreed within about 10% on every snippet, and the table uses o200k. Formatting choices move the counts by roughly ±10%. These are tokens to write the code, and the same tokens are paid each time the code is read back into context.

All pairs measured, o200k tokens (older → newer, ratio): toggle class 46 → 7 (6.6×); lazy image (IntersectionObserver + data-src) 76 → 12 (6.3×); parentNode.removeChild → remove() 7 → 3 (2.3×); Array.reduce grouping → Object.groupBy 32 → 14 (2.3×); manual promise resolvers → Promise.withResolvers() 28 → 13 (2.2×); AbortController + setTimeout → AbortSignal.timeout() 38 → 18 (2.1×); XHR with status and error handling → fetch/await with try/catch 76 → 40 (1.9×); JSON.parse(JSON.stringify()) → structuredClone() 9 → 7 (1.3×); repeated selectors → CSS nesting 48 → 50 (0.96×; with a longer .product-card selector, 53 → 51). The median across the 9 pairs is 2.2×. CSS nesting saves characters (150 → 138) but not tokens: a short, repeated selector is cheap, and the nesting adds indentation and braces.

Counter component (a button showing “Clicked N times”, imports included): vanilla custom element with shadow DOM, constructor, connectedCallback, render() and customElements.define 123; Lit 88; React function component 61; Svelte 5 29. React and Svelte need a build step and React has no style encapsulation, so this is not like-for-like on features. It shows the ceremony gap between the platform's component model and what developers (and agents) reach for. A trap I hit while writing the Lit version: a standard class field (count = 0) silently shadows Lit's reactive accessor, so initialization has to go in the constructor. That is a robustness problem, not a token one.

Libraries vs. platform: $('.item').addClass('active') 8 vs document.querySelectorAll('.item').forEach(el => el.classList.add('active')) 18; delegated click handler, jQuery 24 vs addEventListener + closest() 32. Building a link, createElement + properties + append 24 vs innerHTML += template string 16. The cheapest version is the XSS-prone one, so token efficiency and robustness can pull in opposite directions.

Identifiers. In code context, cl100k encodes .addEventListener, .getElementById and the 23-character .getElementsByClassName each as a single token. o200k splits them at camelCase boundaries (3, 4 and 5 tokens). The 13-character, all-lowercase HTML attribute popovertarget is 4 tokens in all three tokenizers (pop|o|vert|arget), and .adoptedStyleSheets is 5–6. Tokenizer vocabularies are learned from existing code, so old, popular names are cheap and new or unconventionally cased names are fragmented. Even so, identifiers are a small share of a snippet's tokens, and camelCase costs about one token per word. A long, descriptive, familiar name costs little.

Familiarity (second stat). Zixuan Wu, Carolyn Jane Anderson and Arjun Guha, “The Best Programming Language for Tokenmaxxing: An Investigation of Coding Agent Behavior Across Programming Languages”, arXiv:2607.22807 (July 2026, rev. Oct 2026). They gave the same problems to agents in Python, Java, Rust and OCaml. In their Table 19, pooled over the three open models (Gemma, Qwen, GLM), the median final solution is 190 tokens in Python vs 272 in OCaml (1.4×). Median total output is 2,548 vs 6,706 (2.6×). In the authors' words, “The extra cost is not representation.” The extra tokens come from compile errors and error recovery: about 41% of Gemma's OCaml tokens vs about 13% for Python. Caveats: the frontier models had smaller gaps (controlled OCaml/Python output ratios of 1.30× for GPT-5.5 and 1.28× for Sonnet), and this compares languages, not Web APIs. I use it as an analogy for an unfamiliar API.

Read vs write (third stat). Output tokens are generated serially and priced higher. On Anthropic's pricing page (checked 27 Oct 2026), Claude Sonnet 5.5 is $2/MTok input, $0.10 cache hits and $10 output: output costs 5× uncached input and 100× a cached read. Opus 5.5 has the same ratios ($4 / $0.20 / $20). Even so, Longju Bai et al., “How Do AI Agents Spend Your Money? Analyzing and Predicting Token Consumption in Agentic Coding Tasks”, arXiv:2604.22750 (SWE-bench Verified, 8 models, OpenHands), find that “input tokens, not output tokens, dominate the overall cost in agentic coding”. Cache-read input is the largest category, and cost spikes come from actions that bring new content into context, such as viewing files and running tests. So verbose code is paid for once when written and again every turn it sits in context or is re-read. Anthropic's “Writing effective tools for AI agents” (Sep 2025) makes the same point for tool output: a concise response format used 72 tokens vs 206 for a detailed one. It also found that meaningful names beat opaque IDs such as UUIDs.

Related. Martin Alderson, “Which programming languages are most token-efficient?” (Jan 2026; informal, RosettaCode, GPT-4 tokenizer) found a 2.6× gap across 19 languages, with JavaScript the most verbose dynamic language. APL's terseness didn't help, because the tokenizer splits its rare glyphs into several tokens each.

Question for the room. If unfamiliarity costs more than verbosity, should a new API aim to look like what agents already write (a paved cowpath) even when that isn't the cleanest design?

Agents only fix what fails loudly

Silent failures persist

  • 85% of XSS-prone tasks left exploitable by AI-written code
  • 61% of GPT-4o calls to rare APIs invalid, vs. 6% to common ones
  • 70–90% deprecated-API use when surrounding code is old (9–18% if modern)

Loud failures get fixed

  • 99.9% of the same AI-written code passes syntax checks
  • 94% of LLM TypeScript compile errors are type errors; type-checked decoding cuts them 52–75%
  • +20% issues solved when a linter rejects the agent's broken edits (15% → 18%)

CSS drops display: flexbox silently. How should an API that can't throw say so?

Sources: Veracode, 2026 GenAI Code Security Report; Jain et al., ICSE 2025 (CloudAPIBench); Wang et al., ICSE 2025; Mündler et al., PLDI 2025; Yang et al., NeurIPS 2024 (SWE-agent).

Full analysis, data and open threads: analysis/robustness.md.

Claim. Today's models rarely make mistakes that something detects and reports (syntax, types, lint): those get fixed in the loop. What survives are mistakes nothing reports: insecure but working code, plausible calls to APIs the model has rarely seen, and legacy APIs that still work. The web platform is unusually full of the latter: CSS and HTML recover silently by design, deprecated APIs are almost never removed, and the unsafe API (innerHTML) is the shortest one.

Veracode 2026 GenAI Code Security Report (28 Jul 2026; infographic): about 44% of AI code-generation tasks produced code with a risky vulnerability; average security pass rate 56%, “barely changed from 55% in the first report”. Syntax pass rate 99.9% (“Syntax is solved at 99.9%. Security is not.”). Cross-site scripting (CWE-80) pass rate 15%, i.e. 85% failure; log injection (CWE-117) 12%; SQL injection 83%. Model size makes no difference (large 53%, medium 51%, small 51%); best model GPT-5.5 at 68%. Methodology (from the 2025 edition, 30 Jul 2025): 80 curated code-completion tasks in Java, JavaScript, Python and C#, each completable securely or insecurely, run against 100+ LLMs and checked with Veracode's static analysis. The 2025 numbers were 45% vulnerable and 86% XSS failure. Caveats: vendor report; the XSS tasks are mostly server-side output encoding, not DOM innerHTML; prompts don't ask for security. Worth noting in discussion (my interpretation, not Veracode's): SQL injection, where the idiomatic API (parameterized queries) is also the safe one, passes 83%; XSS, where safety means remembering to encode, passes 15%. That is the “pit of success” argument for safe-by-default APIs such as setHTML() and Trusted Types.

Jain et al., “On Mitigating Code LLM Hallucinations with API Documentation” (Amazon; ICSE 2025 SEIP). CloudAPIBench: 622 Python tasks against AWS and Azure SDKs, with API frequency counted in The Stack v2 (low = ≤10 occurrences, high = ≥100). GPT-4o (2024-05-13) made valid API invocations for 93.66% of high-frequency APIs, 78.67% of medium and 38.58% of low-frequency ones (so 6% vs. 61% invalid). Open models were far worse on rare APIs (4–35% valid). Retrieving docs raised GPT-4o's low-frequency score to 47.94% but hurt high-frequency APIs when retrieval was imprecise. Caveats: 2024 model, single-call completions, cloud SDKs rather than web APIs. Relevance: every new web API starts out “low frequency”, which is the session's familiarity-vs-quality problem.

Wang et al., “LLMs Meet Library Evolution: Evaluating Deprecated API Usage in LLM-based Code Completion” (ICSE 2025). 7 LLMs, 145 deprecated→replacement API mappings in 8 Python libraries, 28,125 line-completion prompts taken from real functions. When the surrounding function already used outdated APIs, models picked the deprecated API in 70–90% of the completions that used either the old or the new API; in up-to-date functions, 9–18%; overall 25–38%. (Completions that called either API were only 9–23% of all completions.) Caveats: 2024 models (CodeLlama, StarCoder2, DeepSeek-Coder, GPT-3.5 etc.), Python, not agents. Relevance: the web never removes APIs, so agents editing old pages will keep extending document.write-era patterns unless something tells them not to.

Mündler, He, Wang, Sen, Song, Vechev, “Type-Constrained Code Generation with Language Models” (PLDI 2025). In TypeScript generated by open-weight models (2B–34B), on average 94% of compilation errors are type errors and only 6% syntax errors. Constraining decoding with the type system cut compilation errors by 75.3% (HumanEval) and 52.1% (MBPP) for synthesis, and raised functional correctness by 3.5–5.5% relative. Caveats: small open models, benchmark-style problems, and constrained decoding rather than an agent reading errors. GitHub's Octoverse 2025 post (TypeScript became GitHub's #1 language in August 2025) quotes the same 94% figure: “Type systems reduce ambiguity and catch LLM errors before production.”

Yang, Jimenez et al., “SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering” (NeurIPS 2024). With GPT-4 Turbo on SWE-bench Lite, an edit command that runs flake8 and rejects edits that introduce syntax errors or undefined names resolved 18.0% of issues vs. 15.0% without the check (+20% relative), and 10.3% with plain shell editing. The authors note that commands which “lack immediate feedback” are “silent operations potentially confusing for models to interpret”. 51.7% of trajectories hit at least one rejected edit; agents usually recovered from it (the chance of a successful edit fell from 90.5% to 57.2% after one failure). Caveats: 2024 agent and model, Python.

Also relevant (not on the slide):

  • Hallucinated packages (“slopsquatting”): Spracklen et al. (USENIX Security 2025): 576,000 Python and JavaScript samples from 16 LLMs; at least 5.2% (commercial) and 21.7% (open-source) of referenced packages didn't exist; 205,474 unique invented names. A 2026 replication (Churilov, single-author preprint) on Claude Sonnet 4.6, Claude Haiku 4.5, GPT-5.4-mini, Gemini 2.5 Pro and DeepSeek V3.2: 4.62–6.10%, with 127 names (18 on npm) invented identically by all five models. Improving, but the error is still silent until install time.
  • Chen et al., “Teaching Large Language Models to Self-Debug” (2023): with unit-test or execution feedback, accuracy improved by up to 12%; without any external feedback, only 2–3%. Olausson et al. (ICLR 2024) find self-repair is limited by the quality of the feedback.
  • Yang & Ding, “Signal or Noise? A Benchmark Study of Agent Skills in Web Development” (Aug 2026 preprint): injecting 31 public web-dev “skills” into agent prompts lowered Pass@2 by 1.3–4.2% and raised token cost 72–394%; anti-pattern rules helped more than examples. Telling agents up front is no substitute for the platform telling them at runtime.
  • CSS example: per CSS error-handling rules, an invalid declaration such as display: flexbox is dropped. DevTools' Styles pane marks it, but nothing reaches the console, so an agent that reads console output gets no signal. Possible levers to discuss: console warnings for invalid declarations or deprecated APIs, a reporting or lint channel agents can read, dictionaries instead of positional arguments, precise WebIDL that maps to TypeScript types, and safe defaults.

No TAG principle mentions AI. Where do agents fit in the priority of constituencies?

Sources: W3C TAG Web Platform Design Principles (14 Sep 2026); HTML Design Principles (2007); Extensible Web Manifesto (EWM, 2013); Anthropic; Chrome DevTools MCP; Spracklen et al. 2025. Tokens: o200k. ✓ holds · ? contested · ✗ works against agents

Full analysis, data and open threads: analysis/design-principles.md.

Key claim. The TAG's Web Platform Design Principles (W3C Group Note, 14 Sep 2026) has 100+ numbered sections and never mentions AI, LLMs or language models; every “agent” in it is a user agent. Only one principle names its audience: §2.7 “Design textual formats for humans”. Most of the document still holds: privacy, security, §5.3 don't expose GC, §5.2 run-to-completion and so on protect users from pages, whoever writes the code. The table deliberately picks the author-facing principles where agents change the picture, so it over-represents the contested ones. The ✓/?/✗ verdicts are our opinion; the evidence for each is listed below.

TAG issue tracker. A search of w3ctag/design-principles issues (27 Oct 2026; LLM, AI, agents, agentic, “language model”, copilot, “code generation”) found no issue about agents as API consumers. The only AI issue, #551 (Martin Thomson, Feb 2025), is about sourcing models for in-browser inference APIs. The nearest relevant one is #455 (Lea Verou, Nov 2023, open), which asks that heuristics or “magic” always come with overrides. Martin Thomson's April 2025 comment there argues for avoiding heuristics in new capabilities because sites depend on predictable behavior. That argument also suits agents, which can't observe a heuristic.

Supporting evidence that human and agent ergonomics mostly align. Anthropic, Writing effective tools for agents (11 Sep 2025): “the tools that are most ‘ergonomic’ for agents also end up being surprisingly intuitive to grasp as humans.” OpenAI's function-calling best practices make the human the yardstick: “Pass the intern test: Can an intern/human correctly use the function given nothing but what you gave the model?”

Token counts are our own measurements with OpenAI's public o200k_base tokenizer (via tiktoken), checked against cl100k_base. Claude's tokenizer is not public, so the exact numbers will differ, but the ratios are what matter.

Row by row

1. Use common words (✓). TAG §12.1: “Value readability over brevity. Avoid abbreviations…” Evidence: Anthropic (above) says agents “grapple with natural language names, terms, or identifiers significantly more successfully than they do with cryptic identifiers”, and that resolving UUIDs to meaningful language “significantly improves Claude's precision in retrieval tasks by reducing hallucinations”. It also recommends user_id over user. Wang et al., How Does Naming Affect LLMs on Code Analysis Tasks? (JSEA 2024), found that LLM-based code analysis “heavily relies on well-defined names in code”. That study used older models. Our measurement: common words are cheap tokens: requestAnimationFrame splits into request·Animation·Frame (3) and structuredClone into 2. Abbreviations shatter: RTCDTMFSender splits into RT·CD·TM·FS·ender (5 meaningless fragments). A side note: the casing rule to always capitalize repeated initialisms gives HTML·H·RE·lement for HTMLHRElement, while the “infamous” XMLHttpRequest tokenizes cleanly as XML·Http·Request. Opinion: for names, readability and token efficiency point the same way. An abbreviation saves characters, not tokens.

2. Be consistent (✓, if anything more important). TAG §2.4, §12.5. §2.4 already says “follow the more popular precedent”. Evidence (indirect): Jain et al., On Mitigating Code LLM Hallucinations with API Documentation (2024): “GPT-4o achieves only 38.58% valid low frequency API invocations.” Opinion: for any API it has rarely seen, an agent rebuilds the name and shape from platform-wide patterns. Consistency is what makes that guess right. Humans look things up; agents often don't.

3. Dictionaries, not positional arguments (✓, at a cost). TAG §6.5. Our measurement on the TAG's own examples: new Event("example", { bubbles: true, cancelable: false }) is 15 tokens vs. 9 for new Event("example", true, false) (1.67×). window.scrollBy({ left: 50, top: 0 }) is 14 vs. 9 (1.56×). Both tokenizers give the same counts. Opinion: still worth it. The keys describe themselves when code is read, the “Boolean trap” is exactly where a model has to recall positional meaning, and a few tokens are cheap next to a lookup or a retry. This is a clean case of token efficiency and robustness pulling apart, which is one of the session's questions.

4. Readable over compact formats (?). TAG §2.7: “Favor readability over compactness… SVG path syntax was designed to be compact… the cost to human readability has remained the same.” Our measurement: M10 10 L20 20 is 8 tokens vs. 16 for a hypothetical moveTo(10, 10) lineTo(20, 20). Opinion: compact syntax is cheaper to emit but harder to check, and §2.7's case for lenient syntax (comments, trailing commas) helps agents as much as humans. It is unclear which way agents tip. No direct evidence found.

5. Graceful error recovery (✗ for agents as authors). HTML Design Principles §4.3 Handle Errors (W3C Working Draft, 26 Nov 2007): “Prefer graceful error recovery to hard failure, so that users are not exposed to authoring errors.” See also §2.2 Degrade Gracefully, and CSS 2.1 §4.2: “User agents must ignore a declaration with an unknown property.” Evidence: Chrome's DevTools MCP launch post (Bynens & Hablich, 23 Sep 2025) says coding agents “are not able to see what the code they generate actually does when it runs in the browser. They're effectively programming with a blindfold on.” Wu, Anderson & Guha, The Best Programming Language for Tokenmaxxing (2026), found much of agents' extra cost in unfamiliar languages is error recovery, but compile errors at least give a signal; a CSS typo gives none. Opinion: resilience for end users is right and should stay. The conflict is that recovery is silent at authoring time. TAG §10.7 already requires that developer-facing errors “must be meaningful”, but those messages live in DevTools, which an agent sees only through tooling. A possible way out: make authoring-time diagnostics (dropped declarations, ignored attributes) loud and machine-readable, without changing what users see.

6. Low-level first, libraries on top (?). Extensible Web Manifesto (2013; the original domain now redirects elsewhere): browsers should “provide new low-level capabilities”, so that vendors and library authors can “iterate on libraries that provide developer-friendly, high-level APIs”. TAG §2.2: low-level APIs let “high level APIs… organically emerge from usage patterns”, while high-level APIs give the UA room for accessibility and privacy. Evidence: Twist et al., A Study of LLMs' Preferences for Libraries and Programming Languages (2025): LLMs prioritize “familiarity and popularity over suitability”, and use NumPy unnecessarily in up to 45% of cases. The MDN MCP announcement on the earlier slide says agents “can surface outdated web platform information”. Opinion: the manifesto assumes glue code is expensive for humans, so it is written once in a shared library. Agents make glue cheap but write it fresh for each project, with no shared bug fixes, or fall back on whichever library is most popular. A high-level declarative feature (popover, <dialog>) can be written in one shot and keeps accessibility in the browser, but only once models know it, which takes years.

7. Pave the cowpaths (?). HTML Design Principles §2.4: “When a practice is already widespread among authors, consider adopting it.” Precedent in TAG §2.15: Array.prototype.contains() became includes() because of PrototypeJS. Evidence: Spracklen et al., We Have a Package for You! (USENIX Security 2025): at least 5.2% (commercial) and 21.7% (open-source) of suggested packages were hallucinated, 205,474 unique fake names, and “43% of hallucinated packages were repeated in all 10 queries”. Wang et al., LLMs Meet Library Evolution (ICSE 2025): 25–38% of completions use deprecated APIs, and 70–90% when the surrounding code is outdated. Opinion: paving cowpaths helps agents, because it makes what they already write correct. But as more web code is agent-written, HTTP Archive and use counters measure model priors as much as developer needs. Should the platform pave the APIs agents consistently hallucinate, or does that reward staleness?

Discussion prompt

TAG §1.1: “User needs come before the needs of web page authors, which come before the needs of user agent implementors, which come before the needs of specification writers, which come before theoretical purity.” Are agents “authors”? Or are they a tool that authors use? If they are a tool, §2.15 already has an answer: “Prioritize usability over compatibility with third-party tools… web platform features last a lot longer than most third-party tools.” That is the same objection as the README's, that agents are volatile while Web APIs are permanent. When agent and human DX conflict (rows 3–5), who pays: the human reading the code, or the agent writing it?

Caveats. Most of the LLM studies cited use Python, not web code. The 2007 HTML Design Principles never went beyond Working Draft, though it is still widely cited. The model studies are 2023–2026 and model behavior moves fast, which is the session's own argument about evaluating designs on a delayed feedback loop.

Is the framework now the platform agents target?

Sources: Amplifying, What Claude Code Actually Chooses (Feb 2026); Lovable docs; v0 FAQ; npm registry download API.

Full analysis, data and open threads: analysis/what-agents-write.md.

Claim. When agents build for the web they converge on one framework-shaped stack (React + Tailwind + shadcn/ui + lucide icons), and this is now visible in registry-wide numbers. Whether they also under-use newer native features is plausible but unmeasured: there is no public audit of agent output for <dialog>, popover, :has(), container queries, nesting, View Transitions, anchor positioning, etc. The only number is Chrome's own eval. The gap is itself a finding.

Claude Code picks. Edwin Ong & Alex Vikati (Amplifying), “What Claude Code Actually Chooses”, Feb 2026: Claude Code v2.1.39 on 4 real repos × 3 runs × 3 models (Sonnet 4.5, Opus 4.5, Opus 4.6) × 20 tool categories, open-ended prompts that never name a tool; 2,430 responses, 2,073 with parseable picks. UI components: shadcn/ui 90.1% (64/71). Styling: Tailwind 68.4% (52/76). State: Zustand 64.8% (57/88), Redux 0 primary picks. JS frontend deployment: Vercel 100% (86/86). “Custom/DIY” is the most common single label (12 of 20 categories). Caveats: one agent, small n per category, the page does not break down the non-Tailwind styling picks (e.g. plain CSS vs. CSS Modules) and it measures libraries, not native features. Counterpoint worth raising: “Newer models tend to pick newer tools” (JS ORM: Prisma 79% on Sonnet 4.5 → 0% on Opus 4.6; Drizzle 21% → 100%), so lock-in to the familiar is not absolute; the question is whether native platform features get the same lift.

App builders. v0 FAQ: “v0 uses Next.js, React, TypeScript, Tailwind CSS, and shadcn/ui” (it says it also “supports popular frontend frameworks and UI libraries”). Lovable FAQ: “Lovable does not offer a choice of framework or database.” New Lovable apps since 13 May 2026 use TanStack Start (SSR); before that, React + Vite + React Router, client-rendered (Lovable blog, 1 Jun 2026). That switch is the “framework is the platform” point in miniature: one vendor decision changed the rendering model of every new app overnight, with no user opt-in. Similarly shadcn/ui made Base UI the default primitive layer instead of Radix for new projects (changelog, July 2026). Anthropic's own web-artifacts-builder skill specifies “React 18 + TypeScript + Vite + Parcel + Tailwind CSS + shadcn/ui”. Scale: “100,000 new projects are built on Lovable every single day” (Lovable, 18 Nov 2025, vendor claim). Later totals (50–60M projects, ~1M/week) appear only in secondary sources.

npm downloads (monthly totals, September 2024 vs. September 2026, from https://api.npmjs.org/downloads/point/2026-09-01:2026-09-30/<pkg>, fetched 27 Oct 2026): shadcn CLI 0.78M → 41.1M (53×; shadcn + shadcn-ui combined, because the CLI was renamed from shadcn-ui to shadcn in July 2024; the new name alone is 0.42M → 40.4M, 96×, which overstates the growth); lucide-react 6.9M → 426M (61×); class-variance-authority 7.8M → 266M (34×); tailwind-merge 14.8M → 345M (23×); @radix-ui/react-dialog 14.9M → 297M (20×); tailwindcss 44M → 529M (12×); @floating-ui/dom 51M → 409M (8×); next 30.8M → 243M (7.9×); react 107M → 731M (6.8×); express 135M → 561M (4.1×); lodash 218M → 697M (3.2×); lit 8.2M → 30M (3.7×); svelte 5.6M → 24M (4.3×); vue 22.7M → 66M (2.9×); @angular/core 14.6M → 25M (1.7×); jquery 48.8M → 66M (1.4×). React's share of react+vue+svelte+angular downloads went from 71% to 86%. Bars on the slide are drawn to a linear scale (61× = 80% width). Raw monthly data: data/npm-downloads.csv; the script is tools/npm_downloads.py.

Caveats on npm: downloads are not apps or users. All of npm inflated sharply over 2025–26 (lodash and express, which no one chooses for UI, grew 3–4×; there is a step up across every package around Feb–Mar 2026), most likely because agents and app builders spin up huge numbers of fresh projects and CI installs. That inflation is part of the story, which is why lodash is shown as the baseline. Packages that ship together with shadcn/ui (lucide-react, class-variance-authority, tailwind-merge, Radix) grew 20–60×, far ahead of the baseline. Two of them are JS stand-ins for things the platform now has: Radix Dialog vs. <dialog>/popover, and Floating UI vs. anchor positioning. It shows what gets installed, not whether native features were used alongside.

Native features. Chrome, Modern Web Guidance (announced ~20 May 2026; page updated 30 Jun 2026): “AI coding agents tend to default to older, outdated solutions to modern web development problems” and “AI models historically haven't been aware of—or have incorrect information about—the latest web platform features.” Its evals (Playwright-based, unguided control vs. guided) show “on average… a 37 percentage point improvement in adherence to modern best practices”. Caveats: vendor's own eval, no baseline or per-feature numbers published, no methodology writeup. The repo covers 232 features / 186 use cases. Related tooling that exists specifically to fix this: the MDN MCP server (June 2026) and community Baseline MCP servers built on the web-features data. I found no published audit of agent output for specific native features, and no crawl (HTTP Archive / Web Almanac) that splits AI-built sites from the rest.

Why it happens (the feedback loop). Twist et al., “A Study of LLMs' Preferences for Libraries and Programming Languages” (arXiv 2503.17181, v4 Jun 2026, 8 LLMs): models “overuse widely adopted libraries such as NumPy”, unnecessarily in up to 45% of cases; Python is chosen in 58% of high-performance project setups where it is not suitable, and Rust is never used. The authors warn this creates discoverability problems for newer projects. GitHub (A. Griffiths, 19 Feb 2026) on “convenience loops”: TypeScript became the most-used language on GitHub in Aug 2025 (+66% YoY); “Reduced friction becomes a preference—and preferences at scale can shift ecosystems.”

Homogenization. Anthropic, “Improving frontend design through Skills” (12 Nov 2025) names it “distributional convergence”: without guidance a model will “conform to Inter fonts, purple gradients on white backgrounds, and minimal animations”, because “models predict tokens based on statistical patterns in training data.” Adam Wathan's Aug 2025 tongue-in-cheek apology for Tailwind UI's bg-indigo-500 buttons being why AI UIs are purple is widely reported, but I did not reach the original post. Counterpoint from the Web Almanac 2025 Generative AI chapter (Jan 2026, crawls to Oct 2025): indigo-500 rose from 0.03% to 0.54% of all pages (Q3 2022 → Q4 2025), but within Tailwind pages the “AI colors” stayed at ~2% with no surge, so the rise “may be less a result of AI ‘choosing’ purple and more a reflection of the general rise in Tailwind’s popularity.” Homogenization at the stack level is clearer in the data than at the visual level.

Discussion. Two readings: (1) freeze: new platform features never reach agents' defaults, so they never get the usage that would put them in training data; (2) the framework is the platform: a handful of defaults (v0, Lovable, shadcn/ui, Tailwind) decide what millions of apps use and can change overnight, so the fastest route to adoption of a native feature may be getting it into those defaults. Does that change who standards work should be designed for?

Evals reward the familiar

  • 1.3–1.7× tokens in OCaml vs. Python on the same tasks, mostly fixing failed attempts
  • 25–38% of completions choose a deprecated API over its replacement
  • 53% → 100% pass rate on Next.js 16 APIs absent from training data, once docs are in context

So how do we evaluate a design that is better, but new?

Sources: Liang et al., RustEvo² (2025); Wu, Anderson & Guha (2026); Wang et al., ICSE 2025; Vercel (Jan 2026).

Full analysis, data and open threads: analysis/evaluation.md.

Point of the slide: an API’s measured cost to an agent mixes two things, how good the design is and how much of it the model has seen. Every study below finds the second one is large, so any evaluation we run today on a new design (or a new design principle) is biased toward what is already in the training data. The question for the room: if every measurement we can run today rewards what models have already seen, and training data takes years to catch up, how do we evaluate a design (or a design principle) that is better but new?

Liang et al., RustEvo²: An Evolving Benchmark for API Evolution in LLM-based Rust Code Generation, arXiv 2503.16922, March 2025. 588 real Rust API changes turned into coding tasks. Table 3: tasks on APIs from Rust 1.71–1.73 (before every tested model’s cutoff, 204 tasks) vs. Rust 1.81–1.84 (after, 220 tasks), averaged over DeepSeek-v3, Gemini 2.0 Flash, Gemini 1.5 Pro, Llama 3.1 70B and o1-mini. Pass@1 without API info: 56.1% before vs. 32.5% after. With the API’s information in the prompt: 70.9% vs. 41.4%. Separately (Table 4, a different 5-model set including Claude 3.7 Sonnet and GPT-4o), RAG raised post-cutoff tasks from 34.9% to 48.4% (+13.5 points). Caveats: the before and after task sets use different APIs, so task difficulty is not controlled; models are early-2025 vintage. Still, note that docs in the prompt help the familiar APIs more (+14.8 points) than the unfamiliar ones (+8.9).

Wu, Anderson & Guha, The Best Programming Language for Tokenmaxxing, arXiv 2607.22807, July 2026. Five models (Claude Sonnet 4.6, GPT-5.5, GLM-5.2, Qwen3.6, Gemma 4) on the same 100 LiveCodeBench problems in Python, Java, Rust and OCaml, with a mixed-effects model controlling for problem difficulty. OCaml costs 1.28× (Sonnet), 1.30× (GPT-5.5), 1.44× (Gemma), 1.54× (GLM) and 1.69× (Qwen) the output tokens of Python, significant for every model. The final OCaml solutions are about the same size as Java and Rust ones (median 272 vs. 276 and 303 tokens); the extra tokens go to non-compiling attempts, debugging and reverting, and agents “sidestep unfamiliar target languages by prototyping in Python”. Pass rates barely move for frontier models, so the familiarity penalty shows up as cost, not as failure. Caveat: languages, not APIs, and the link to training-data volume is the authors’ hypothesis (The Stack v2 has ~200 GB of Python/Java, 12 GB of Rust, less OCaml), not something they test.

Wang et al., LLMs Meet Library Evolution: Evaluating Deprecated API Usage in LLM-based Code Completion, ICSE 2025. 145 deprecated→replacement API pairs in 8 Python libraries, 28,125 completion prompts, 7 models. Among completions that use either API, 25–38% use the deprecated one (GPT-3.5: 37.4%); 70–90% when the surrounding code is outdated, 9–18% when it is up to date. Caveat: small 2023-era models plus GPT-3.5; Python, not web APIs. The web parallel would be XHR vs. fetch() or float layouts vs. grid, but I found no equivalent measurement for web platform APIs.

Vercel, AGENTS.md outperforms skills in our agent evals, 27 Jan 2026. Eval suite of Next.js 16 APIs “that aren’t in current model training data” ('use cache', connection(), forbidden()…). Pass rate: 53% with no docs; 53% with a docs skill the agent could invoke (it did not, in 56% of cases); 79% when told to use the skill; 100% with an 8 KB compressed docs index in AGENTS.md. Caveats: vendor eval, model not named, small suite revised during the study.

Other evidence, for discussion:

  • Twist et al., ACL Findings 2026: LLMs overuse popular libraries such as NumPy, “in up to 45% of cases” where they are not needed; they “prioritise familiarity and popularity over suitability”.
  • Jain et al., 2024 (CloudAPIBench): GPT-4o makes valid calls to low-frequency APIs only 38.58% of the time; documentation retrieval raises that to 47.94%, but naive retrieval hurts high-frequency APIs by up to 39 points. Docs are not free for familiar APIs.
  • GitChameleon 2.0 (NeurIPS 2025): on version-specific Python problems, frontier models (GPT-4.1, Claude 3.7 Sonnet, Gemini 2.5 Pro, o1) solve only 48–51%; RAG adds up to ~10 points.
  • MDN MCP server, June 2026: informally, Claude Code (Opus 4.7) without the MCP got browser support right for only 1 of 4 features new in Firefox 151.
  • Chrome’s Modern Web Guidance (I/O 2026) runs evals to “prune lowest-common-denominator content that models already know”, i.e. it already measures familiarity. Its docs claim “on average… a 37 percentage point improvement in adherence to modern best practices”, with no methodology or per-feature numbers published.
  • Lag: model release trails training cutoff by a few months (Claude Opus 5.5: cutoff June 2026), but what matters is how much code using a feature exists by then. Cheng et al., 2024 found effective cutoffs often trail reported ones, because new crawls contain a lot of old content. I found no study measuring model uptake of newly Baseline web features (:has(), nesting, popover, View Transitions, anchor positioning).

Existing attempts to evaluate API design itself, and ways to separate familiarity from design:

  • ADK Arena, June 2026 (“LLM-as-a-Developer”): hold the agent constant, vary the framework, use generation cost as a proxy for API usability (5.6× spread across 51 Python agent frameworks). It does not control for familiarity.
  • Trivedi & Schmitt, 2026: minimal pairs of repos that differ only in cleanliness; same pass rate, but 7–8% fewer tokens on clean code. The same design could compare two API shapes with equal (zero) familiarity.
  • Unseen or renamed APIs: Zan et al., EMNLP 2022 built “private library” benchmarks (MonkeyEval, BeatNumEval) by renaming every pandas/NumPy keyword (pandas→monkey, DataFrame→KnowledgeFrame, isin→iscontain). Identical design, new names: Codex 12B fell from 18.88% to 1.47% pass@1. This is the cleanest measurement of familiarity alone, though on a 2022 model. CodeUpdateArena uses synthetic API updates. Synthetic APIs remove the familiarity term, but also the transfer from similar APIs that real designs benefit from.
  • Anthropic, Writing effective tools for agents (Sep 2025): tool design is iterated with evals tracking tokens, tool calls and errors on held-out tasks; naming choices have “non-trivial effects” that vary by model.

Possible directions to put to the room: compare designs with docs in context for both; use fresh or renamed APIs so neither side is familiar; report tokens and turns as well as pass rate; re-run the same eval as each model generation ships, to see whether the gap closes.

“It's a pre-existing flake”

  • 70 of 311 sessions hit a flaky browser test
  • 49 of them moved on without finding the cause
  • 10 sessions waved off the same dialog race
  • ~10 h of agent time lost to flakes

The usual cause: browser state with no observable “done”, such as an IndexedDB commit, a render, a hash navigation or a popover opening. Tests sleep, then flake.

Should async platform state always expose a completion signal agents can wait on?

Source: our own Claude Code sessions, Jul–Oct 2026 (see notes). Pattern P6 in agent-session-patterns.csv.

Analysis: analysis/agent-sessions.md, example 1.

83 episodes in 70 of 311 sessions (zpcrweb 42, meshcore-web 28); tests surfaced 65. In 49 sessions the agent called the failure “flaky”, “pre-existing” or “environmental” without a root cause; 19 found the cause; 2 found the wrong one. The channel-details dialog race was dismissed in 10 sessions, a hash deep-link race in 6. A dismissal cost about 1 extra suite run and 2.5 min; a root-cause hunt about 7 runs, 34 tool calls and 14 min. Worst case: 51 min and 117 tool calls, then declared “environmental” (session 01Jww63r). About 570 min (~10 h) in total, or 845 min including one deliberate 4.6 h flake hunt the user asked for.

Root causes, where found: popstate and hashchange fire separately for one hash navigation; a write-behind IndexedDB flush with nothing to await; a dialog read before its async-loaded content rendered; a popover show racing mount. A sub-case (9 episodes): IndexedDB is per-origin and persistent, so state leaked between test pages. One leak added 26 s to every suite run (deleteDatabase blocked by 25 open tabs). In another, parallel test iframes deleted each other's databases.

Quote: session 0199FRBg, 29 Jul 2026. Caveat: many of these are app or test-harness bugs, not platform flaws. The platform question is why “wait until it's done” is so often impossible to express.

Agents go to extreme lengths to route around the platform. Which gaps should we close?

Source: our own Claude Code sessions, Jul–Oct 2026 (see notes). Patterns P8, P9 and P10.

Analysis: analysis/agent-sessions.md, examples 9 and 11–13.

Layout. 38 episodes in 30 sessions of ad-hoc CDP measurement scripts (often numbered: zzmeasure…zzmeasure5, dbgwide1..5, anim1..6) and screenshot→tweak loops: 71 probe calls and 121 screenshot reads. All 24 user-reported CSS bugs were missed by the agent. Where we can tell (14 cases), 11 had already been “verified”. Causes the screenshots didn't show: border-collapse tie rules, table-layout: auto widening columns with two-digit headers, flex: 1 meaning a 0% basis, sticky with no z-index, an auto track plus aspect-ratio, and a fixed 599px breakpoint standing in for “content no longer fits” (it overflowed at ~780px). One stand-out silent failure: min(1fr, 19px) is invalid, so the whole grid-template-columns was dropped and a 96-well grid collapsed to one 281px column. Only 4 probe scripts revealed it. Agent, 017ep63t: “Measured rather than eyeballed, since ‘looks fine in a screenshot’ is how this slipped through in the first place.”

Extreme measures. When a platform API didn't fit, agents often reimplemented the platform instead of adapting. A deterministic device emulator needed synchronous hashing. The agent measured “0 of 50 SHA-256 digests done” by setTimeout(0) and wrote ~300 lines of SHA-256/512, HMAC, Ed25519 and X25519 in BigInt (01PJZjFt). For a PNG chart export it wrote a software rasterizer, PNG encoder and 5×7 pixel font, 728 lines over 78 tool calls. The user: “much of the new 728 lines of code are because we refused to take a dependency … that seems silly to reimplement ourselves” (01HvAN6f). It was redone as a headless-Chrome screenshot. IndexedDB has no partial update, so appending ~1 MB rewrote ~45 MB, which led to three schema redesigns over two days (worst session 286 tool calls, ~2 h).

Across 15 such episodes: ~1,900 lines hand-written, ~800 later deleted. Caveat: some of this is agent judgement (taking a dependency was an option), not only missing primitives. In 3 cases the feature existed (anchor positioning, popover=hint, overflow-anchor) but the agent avoided it over cross-browser worries in a Chromium-only app.

How can agents verify behaviour that only exists on a real device?

Source: our own Claude Code sessions, Oct 2026 (see notes). Pattern P11.

Analysis: analysis/agent-sessions.md, example 14.
