## Question

> What makes a Web API robust for agents, i.e. harder to misuse? How do
> agents actually misuse web APIs today?

Sub-questions:

- Which kinds of mistakes do coding agents and LLMs make with APIs, and how often?
- Which of those mistakes get fixed in the agent's own loop, and which reach production?
- Which API design properties make the difference, and what does that mean for the web platform, which (unlike most ecosystems) recovers silently from many errors and almost never removes APIs?

## Key findings

The short version: **agents fix what fails loudly. Mistakes that nothing
reports are the ones that ship.**

- **Loud errors are basically solved.** In Veracode's 2026 test of
  AI-generated code, 99.9% passes syntax checks, but only 56% passes
  security checks. That 56% is “barely changed from 55%” in the first report
  (2025). — Veracode, *2026 GenAI Code Security Report*.
- **Silent, unsafe defaults are where code fails worst.** AI-written code
  failed to protect against cross-site scripting (CWE-80) **85%** of the time
  (15% pass rate) and against log injection (CWE-117) 88% of the time (12%
  pass). For SQL injection, where the idiomatic API (parameterized queries)
  is also the safe one, the pass rate is **83%**. Model size makes no
  difference (large 53%, medium 51%, small 51%). — Veracode 2026; 2025
  edition: 45% vulnerable, 86% XSS failure.
- **Rarely used APIs get hallucinated.** GPT-4o made valid calls to **93.66%**
  of frequently used cloud APIs but only **38.58%** of rarely used ones, so
  6% vs. 61% invalid. Open code models managed only 4–35% on rare APIs.
  Every new web API starts out rare. — Jain et al., CloudAPIBench, ICSE 2025.
- **Legacy context breeds legacy code.** When the surrounding function
  already used outdated APIs, models picked the deprecated API in
  **70–90%** of the completions that used either the old or the new API. In
  up-to-date functions the rate was **9–18%**, and 25–38% overall. — Wang et
  al., ICSE 2025.
- **Most LLM compile errors are type errors, and type checking catches
  them.** In TypeScript generated by open models, on average **94%** of
  compilation errors fail type checks and only 6% are syntax errors.
  Constraining generation with the type system cuts compilation errors by
  **75.3%** (HumanEval) and **52.1%** (MBPP). — Mündler et al., PLDI 2025.
  GitHub's Octoverse 2025 post quotes the same 94% figure.
- **Feedback during editing measurably helps agents.** SWE-agent with GPT-4
  Turbo resolved **18.0%** of SWE-bench Lite issues when its edit command ran
  a linter and rejected broken edits, against **15.0%** without the linter
  (+20% relative) and 10.3% with plain shell editing. The authors call
  commands that “lack immediate feedback” “silent operations potentially
  confusing for models to interpret”. — Yang et al., NeurIPS 2024.
- **Invented package names are fewer but persistent.** Package hallucination
  fell from 5.2% (commercial models) and 21.7% (open models) in 2024 to
  **4.62–6.10%** for 2026 frontier models. Even so, 127 invented names (18 of
  them on npm) were produced identically by all five 2026 models. —
  Spracklen et al., USENIX Security 2025; Churilov 2026 preprint.
- **Execution feedback beats self-reflection.** Self-debugging with unit-test
  or execution feedback improved accuracy by up to **12%**. Without external
  feedback the gain was only **2–3%**. — Chen et al. 2023. Olausson et al.
  (ICLR 2024) found that self-repair is limited by the quality of the
  feedback.
- **Instructions are a weak substitute for runtime signals.** Injecting 31
  public web-dev “skills” into agent prompts *lowered* Pass@2 by 1.3–4.2%
  and raised token cost by 72–394%. Anti-pattern rules helped more than
  example-heavy content. — Yang & Ding, Aug 2026 preprint.
- **The web platform is full of silent failure modes,** and I found no
  study that measures agents against them specifically: invalid CSS
  declarations are dropped without a console message, `innerHTML` is the
  shortest way to insert markup, and deprecated APIs keep working. See
  [Web-platform failure modes](#web-platform-failure-modes) and
  [Open threads](#open-threads).

## Evidence from the literature

### Veracode, *GenAI Code Security Report* (2025 and 2026 editions)

- **Citation:**
  - Veracode, *2025 GenAI Code Security Report*, 30 Jul 2025 ([press release](https://www.veracode.com/press-release/ai-generated-code-poses-major-security-risks-in-nearly-half-of-all-development-tasks-veracode-research-reveals/), [report page](https://www.veracode.com/resources/analyst-reports/2025-genai-code-security-report/), October 2025 update).
  - Veracode, *2026 GenAI Code Security Report*, 28 Jul 2026 ([blog](https://www.veracode.com/blog/2026-genai-code-security-report-ai-risk), [infographic](https://www.veracode.com/wp-content/uploads/2026-GenAI-Report-Infographic.pdf)).
- **Measured:** 80 curated code-completion tasks in Java, JavaScript, Python and C#. Each task can be completed securely or insecurely, and the prompt does not ask for security. The tasks ran against 100+ LLMs, and the output was scanned with Veracode's static analysis.
- **Numbers:** See [Data](#veracode-genai-code-security-report-security-pass-rates).
  - 2026: 99.9% syntax pass, 56% security pass (44% vulnerable), XSS pass 15%, log injection 12%, SQL injection 83%, crypto 87%. Size makes no difference; GPT-5.5 is best at 68%.
  - 2025: 45% vulnerable, XSS failure 86%, log injection failure 88%, Java >70%, the other languages 38–45%.
- **Why it matters:** This is the cleanest contrast between errors that are loud (syntax, solved) and silent (security, flat for a year). The gap between SQL injection (83%) and XSS (15%) suggests that when the idiomatic API is the safe one (parameterized queries), models get it right. When safety needs an extra step (encoding output), they don't. That interpretation is mine, not Veracode's, but it is the “pit of success” argument for safe-by-default HTML insertion (`setHTML()`, Trusted Types).
- **Limitations:**
  - It's a vendor report, and the full task set is not public.
  - The XSS tasks are mostly server-side output encoding, not DOM `innerHTML`.
  - These are single completions, not agents with a browser.
  - JavaScript-specific figures are not broken out in the public material.

### Jain et al., “On Mitigating Code LLM Hallucinations with API Documentation” (CloudAPIBench)

- **Citation:** Nihal Jain, Robert Kwiatkowski, Baishakhi Ray, Murali Krishna Ramanathan, Varun Kumar. ICSE 2025 (Software Engineering in Practice). [arXiv:2407.09726](https://arxiv.org/abs/2407.09726).
- **Measured:** Whether a single generated call binds to the real API signature, checked against stubs generated from the docs. 622 synthetic Python tasks for AWS and Azure SDKs, bucketed by how often each API occurs in The Stack v2.
- **Numbers:** GPT-4o got 93.66% valid on high-frequency APIs, 78.67% on medium and 38.58% on low. The best open model on low-frequency APIs was DeepSeekCoder-33B at 34.83%. Documentation retrieval raised GPT-4o's low-frequency score to 47.94% but hurt high-frequency APIs when retrieval was imprecise. The paper names three failure types: non-existent APIs, wrong usage of the right API, and the wrong existing API.
- **Why it matters:** This quantifies the session's “familiar beats better” problem. A brand-new web API is a low-frequency API by definition until training data catches up. Docs help but don't close the gap.
- **Limitations:** 2024 models; cloud SDKs, not web APIs; single-call completion with no agent loop or error feedback. Today's frontier models with tool access are likely better.

### Wang et al., “LLMs Meet Library Evolution: Evaluating Deprecated API Usage in LLM-based Code Completion”

- **Citation:** Chong Wang, Kaifeng Huang, Jian Zhang, Yebo Feng, Lyuye Zhang, Yang Liu, Xin Peng. ICSE 2025. [arXiv:2406.09834](https://arxiv.org/abs/2406.09834) (first titled “How and Why LLMs Use Deprecated APIs in Code Completion? An Empirical Study”).
- **Measured:** Line-level completions at the point of an API call in real functions. There were 145 deprecated→replacement mappings across 8 Python libraries, and 28,125 prompts from 9,022 outdated and 19,103 up-to-date functions. The 7 models were CodeGen-350M/2B/6B, DeepSeek-Coder-1.3B, StarCoder2-3B, CodeLlama-7B and GPT-3.5.
- **Numbers:** DUR (among completions using either the old or the new API) was 69.7–90.0% in outdated contexts and 9.0–17.8% in up-to-date contexts; overall it was 25–38%, higher for larger models. The ReplaceAPI decoding fix exceeded 85% fix rates; a prompt hint did not work well.
- **Why it matters:** Models copy the era of the code around them. The web never removes APIs, so agents maintaining old pages will keep extending `document.write`, synchronous XHR and similar patterns unless something tells them at the point of use. A hint in the prompt was not enough.
- **Limitations:** Small or old models, Python libraries rather than browser APIs, and completion rather than agentic editing. Only a minority of completions (AUP 9–23%) used either API at all.

### Mündler et al., “Type-Constrained Code Generation with Language Models”

- **Citation:** Niels Mündler, Jingxuan He, Hao Wang, Koushik Sen, Dawn Song, Martin Vechev. PLDI 2025 (PACMPL, [doi:10.1145/3729274](https://doi.org/10.1145/3729274)). [arXiv:2504.09246](https://arxiv.org/abs/2504.09246).
- **Measured:** TypeScript synthesis, translation and repair on HumanEval and MBPP, using 6 open models (2B–34B), with and without decoding constrained by a type checker.
- **Numbers:** 94% of compile errors are type errors and 6% syntax errors. Type constraining cut compile errors by 75.3% (HumanEval) and 52.1% (MBPP) in synthesis, and raised functional correctness by 3.5–5.5% relative. Syntax-only constraining could at best remove 9.0% and 4.8%.
- **Why it matters:** For code from today's models, the useful checks are semantic (types, and by extension precise WebIDL that maps to TypeScript types), not syntactic. Strong, precise types are a robustness lever. GitHub's [Octoverse 2025](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/) post quotes the 94% figure to explain TypeScript becoming GitHub's #1 language (August 2025): “Type systems reduce ambiguity and catch LLM errors before production.”
- **Limitations:** Small open models on benchmark problems. Constrained decoding is not the same as an agent reading `tsc` output. The paper's text and its Table 2 caption give slightly different reduction figures (see [Caveats](#caveats)).

### Yang et al., “SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering”

- **Citation:** John Yang, Carlos E. Jimenez, Alexander Wettig, Kilian Lieret, Shunyu Yao, Karthik Narasimhan, Ofir Press. NeurIPS 2024. [arXiv:2405.15793](https://arxiv.org/abs/2405.15793).
- **Measured:** Ablations of the agent's tool interface on SWE-bench Lite (300 Python issues) with GPT-4 Turbo.
- **Numbers:** 18.0% resolved with a linter-guarded edit command, 15.0% without the linter and 10.3% with shell-only editing. 51.7% of trajectories had at least one rejected edit. The chance an edit eventually succeeds is 90.5%, dropping to 57.2% after one failure. Too much context also hurt: viewing the full file gave 12.7%, and keeping the full history gave 15.0%.
- **Why it matters:** This is the most direct causal evidence that immediate, specific error feedback at the point of the mistake improves agent outcomes. The authors explicitly flag silent operations as confusing for models. Web APIs that fail silently are, in effect, edit commands without the linter.
- **Limitations:** 2024 model and agent, Python. The +3-point gain comes from 300 issues, so it is noisy.

### Spracklen et al., “We Have a Package for You! A Comprehensive Analysis of Package Hallucinations by Code Generating LLMs”

- **Citation:** Joseph Spracklen, Raveen Wijewickrama, A H M Nazmus Sakib, Anindya Maiti, Bimal Viswanath, Murtuza Jadliwala. USENIX Security 2025. [arXiv:2406.10279](https://arxiv.org/abs/2406.10279).
- **Measured:** Package names referenced in 576,000 Python and JavaScript samples from 16 models (2024), checked against the PyPI and npm package lists.
- **Numbers:** 19.7% of 2.23M package references were hallucinated, with 205,474 unique invented names. Commercial models hallucinated at least 5.2% of packages and open models 21.7%. JavaScript was worse than Python (21.3% vs. 15.8%). 43% of hallucinated names repeated in all 10 reruns.
- **Why it matters:** This is the canonical “slopsquatting” result. A hallucinated name fails silently until install time, or never if an attacker has registered it.
- **Limitations:** 2024 models, and package names rather than API members.

### Churilov, “The Range Shrinks, the Threat Remains: Re-evaluating LLM Package Hallucinations on the 2026 Frontier-Model Cohort”

- **Citation:** Aleksandr Churilov (independent researcher). arXiv preprint, May 2026, revised Aug 2026. [arXiv:2605.17062](https://arxiv.org/abs/2605.17062).
- **Measured:** A replication of Spracklen's method on Claude Sonnet 4.6, Claude Haiku 4.5, GPT-5.4-mini, Gemini 2.5 Pro and DeepSeek V3.2, over 199,845 prompts.
- **Numbers:** 4.62–6.10% overall. JavaScript is now lower than Python (2.62–3.78% vs. 5.49–7.27%). 127 names were shared by all five models, 53 of which were still registrable.
- **Why it matters:** Frontier models have improved a lot on the worst case but not on the best case. The remaining errors are consistent across vendors, which makes them exploitable.
- **Limitations:** Single-author preprint, not peer reviewed.

### Chen et al., “Teaching Large Language Models to Self-Debug”

- **Citation:** Xinyun Chen, Maxwell Lin, Nathanael Schärli, Denny Zhou. arXiv 2023; ICLR 2024. [arXiv:2304.05128](https://arxiv.org/abs/2304.05128).
- **Numbers:** Up to +12% accuracy with unit-test or execution feedback, and +2–3% with self-explanation only.
- **Why it matters:** External signals do most of the work.
- **Limitations:** 2023 models; text-to-SQL and Python benchmarks.

### Olausson et al., “Is Self-Repair a Silver Bullet for Code Generation?”

- **Citation:** Theo X. Olausson, Jeevana Priya Inala, Chenglong Wang, Jianfeng Gao, Armando Solar-Lezama. ICLR 2024. [arXiv:2306.09896](https://arxiv.org/abs/2306.09896).
- **Finding:** Cost-matched self-repair gains are “often modest … sometimes not present at all”. Better feedback, from a stronger model or from humans, gives substantially larger gains.
- **Why it matters:** The quality of the error signal is the bottleneck, which argues for platform error messages that are specific and actionable.

### Yang & Ding, “Signal or Noise? A Benchmark Study of Agent Skills in Web Development”

- **Citation:** Ziyue Yang, Fan Ding. arXiv preprint, 24 Aug 2026. [arXiv:2608.23067](https://arxiv.org/abs/2608.23067).
- **Numbers:** See [Data](#agent-skills-for-web-development-webdev-skills-bench). Skills lowered Pass@2 by 1.3–4.2% at 72–394% more tokens.
- **Why it matters:** Putting guidance into agent context (for example “use `textContent`, not `innerHTML`”) is not a reliable substitute for an API that is hard to misuse or that reports misuse at runtime.
- **Limitations:** Preprint. Specific to the public skills tested and to Web-Bench.

### Also seen, not used

- **Human studies of error-message quality:**
  - [Santos & Becker 2024](https://arxiv.org/abs/2409.18661): GPT-4-rewritten compiler errors beat standard ones in only 1 of 6 tasks for 106 students.
  - A [2026 preprint](https://arxiv.org/abs/2608.20896): adaptive LLM explanations gave no significant gain in fix rate.

  Both are about humans, not agents. They suggest that verbosity doesn't equal helpfulness, so error messages for agents should be precise rather than long.
- **Boris Cherny (creator of Claude Code):** “give Claude a way to verify its work … it will 2-3x the quality of the final result”. This is widely quoted from a social-media thread (late 2025 or Jan 2026). I could not reach the original post, and it is an anecdote, not a measurement.
- **Other front-end benchmarks:** [DesignBench](https://arxiv.org/abs/2506.06251) found that framework compile errors in React are mostly syntax and `"use client"` errors. [FrontendBench](https://arxiv.org/abs/2506.13832) has 148 HTML/CSS/JS tasks scored by Jest/Puppeteer tests. Neither measures silent CSS or HTML failures.

## Web-platform failure modes

The web platform is unusually forgiving, by design (robustness principle,
“don't break the web”). For a human with eyes on the page, forgiveness is a
feature. For an agent that judges success from console output, tests or
the DOM, it removes the error signal. Catalogue (illustrative; I found no
study measuring agents on these specifically):

| Failure mode | What happens | Signal an agent gets today | Evidence it matters |
|---|---|---|---|
| Invalid CSS declaration (`display: flexbox`, typo'd property, wrong unit) | The declaration is dropped under CSS error-handling rules | None in the console. DevTools' Styles pane marks it with a warning icon | Analogy: SWE-agent's linter (+20%); 99.9% syntax pass vs. silent errors |
| Unsafe HTML insertion (`innerHTML`, `insertAdjacentHTML`, `document.write`) | Works, and is exploitable | None, unless Trusted Types or CSP is enforced | Veracode: XSS pass rate 15% |
| Deprecated but working APIs (sync XHR, `document.write`, `unload`, `keyCode`, legacy `addListener`) | Works, sometimes with a deprecation warning in DevTools Issues | Inconsistent: some APIs warn in the console, many don't | Wang et al.: 70–90% deprecated use in legacy contexts |
| Rare or new APIs | Plausible but wrong member names or argument shapes; often `TypeError: x is not a function` (loud), but option-dictionary typos are ignored (silent) | Loud for missing methods; silent for unknown dictionary members | CloudAPIBench: 61% invalid on rare APIs |
| Unknown dictionary members (`{passive: true, once: ture}`, misspelled `addEventListener` options) | WebIDL ignores unknown dictionary keys | None | (hypothesis: no study found) |
| Invalid enum or attribute values in HTML (`<input type=emial>`, `loading=lazyy`) | Falls back to the default | None (HTML validator only) | (hypothesis) |
| Forgotten `await` / unhandled promise | Code runs out of order; rejections may only log `Uncaught (in promise)` | Partial | (hypothesis; TypeScript's `no-floating-promises` lint exists for this) |
| Feature used beyond its Baseline status | Works in the agent's test browser, fails elsewhere | None in a single-browser loop | (hypothesis) |
| Hallucinated npm package | Install fails (loud) or installs an attacker's package (silent) | Depends | Spracklen; Churilov |

**Design levers identified** (each paired with the evidence that supports
the principle):

1. **Safe defaults / pit of success.** Make the shortest, most familiar
   call the safe one: `setHTML()` (Sanitizer API) over `innerHTML`, and
   Trusted Types. Evidence: the gap between SQL injection (83%) and XSS
   (15%) in Veracode 2026.
2. **Fail loudly, or at least report.** Where the platform can't throw for
   compatibility reasons (CSS, HTML parsing, unknown dictionary members),
   add a channel an agent can read: console warnings for invalid
   declarations and deprecated APIs, the Reporting API (for example
   deprecation reports via `ReportingObserver`), or a DevTools Issues
   export over CDP/WebDriver BiDi. Evidence: SWE-agent's linter ablation;
   Chen et al. on execution feedback.
3. **Precise types.** Tight WebIDL (enums instead of free strings, no
   `any`) that generates precise TypeScript definitions. Evidence: 94% of
   LLM compile errors are type errors, and type constraining cuts them
   52–75%.
4. **Dictionaries over positional arguments; no ambiguous overloads.**
   Named members are self-describing and order-independent, but only robust
   if typos are reported (see the unknown-members row above). Evidence:
   CloudAPIBench's “incorrect usage of the target API” failure class.
   There is no direct measurement for the web.
5. **Consistency with existing patterns.** New APIs that look like what
   models already know behave more like high-frequency APIs. Evidence:
   CloudAPIBench's frequency gradient. There is tension here with
   “better” designs (see the session's evaluation question).
6. **Deprecations that speak at the point of use.** A prompt-level hint
   barely worked in Wang et al., while a decode-time replacement fixed more
   than 85%. The web equivalent of a decode-time replacement is a
   point-of-use warning or report, not a note in documentation.
7. **Don't rely on documentation or skills alone.** DAG helps rare APIs
   but hurts common ones when imprecise. Web-dev skills reduced pass rates.

## Methodology

- I started from the session question and the candidate topics in the
  brief: package hallucination, API hallucination, deprecated APIs,
  security of LLM code, web failure modes, feedback loops.
- I searched with web search for each topic, then fetched the primary
  sources. For the arXiv papers (CloudAPIBench, Wang et al., Mündler et
  al., SWE-agent, Spracklen et al., Churilov) I downloaded the PDFs and
  extracted the exact numbers from tables and text with `pdftotext`. Every
  number above was read from the source, not from secondary coverage.
- For Veracode, I used the vendor's own pages: the 2025 press release, the
  2026 blog post and the 2026 infographic PDF. The full PDF report sits
  behind a form and was not read.
- For Chen et al., Olausson et al. and Yang & Ding, I read the arXiv
  abstract pages.
- I searched specifically for web-platform studies (LLMs and Baseline,
  LLM-generated CSS validity, silent CSS failures, deprecated web APIs in
  LLM output) and found none. The web-platform catalogue above is therefore
  illustrative, and the corresponding rows are marked as hypotheses.
- I discarded claims I couldn't trace to a primary source, for example the
  Boris Cherny “2–3×” quote, which is kept only as an anecdote.

## Caveats

- **Model age:** Apart from Veracode 2026 and Churilov 2026, the studies use
  2023–2024 models, often small open ones. Frontier agents in late 2026 are
  likely better on all of these, although Veracode shows the security pass
  rate barely moved between 2025 and 2026.
- **Not web APIs:** None of the quantitative studies measure *web platform*
  APIs specifically. They cover Python libraries, cloud SDKs, TypeScript
  benchmarks and multi-language security tasks. The leap to the web is an
  argument by analogy.
- **Completions, not agents:** Most studies test single completions without
  a feedback loop. SWE-agent is the main exception.
- **Veracode is a vendor** and its methodology is only partly public. The XSS
  tasks are likely server-side encoding, not DOM sinks. The interpretation
  of SQL injection vs. XSS is mine.
- **Mündler et al. internal inconsistency:** v2's text says 75.3% / 52.1%
  compile-error reduction, while the Table 2 caption says 74.8% / 56.0%. The
  slide uses the text's 52–75%.
- **Wang et al.'s DUR** is a share of *plausible* completions, those that
  used either the deprecated API or its replacement, which were only 9–23%
  of completions. The slide's “70–90% deprecated-API use” should be read
  that way. The deck's speaker notes say “used the deprecated API 70–90% of
  the time”, which is a slight simplification.
- **Small samples:** SWE-agent's +3 points come from 300 issues.
- **Preprints:** Churilov (2026) and Yang & Ding (2026) are single
  preprints and not peer reviewed.

## Open threads

- **A web-specific CloudAPIBench.** Measure valid-invocation rates for web
  APIs bucketed by age, Baseline status or Chrome Status ship date, and by
  frequency in a crawl such as HTTP Archive. Does “newly Baseline” behave
  like “low frequency”? Could reuse `web/data/chromestatus-features.csv`.
- **A web-specific Veracode.** Front-end tasks with a DOM XSS sink, scored
  for `innerHTML` vs. `textContent` / `setHTML()`, with and without Trusted
  Types enforced (does a loud CSP/Trusted Types error get the agent to fix
  it?).
- **The silent-CSS experiment.** Give agents layout tasks and count
  invalid or ignored declarations in the final CSS. Compare a loop with only
  console output against one that also gets DevTools Issues or CSS parse
  warnings (for example via CDP `CSS` domain or `Audits.issueAdded`). This
  is a direct test of the “fail loudly” lever on the web.
- **Do agents read DevTools Issues and deprecation reports?** Check whether
  current coding agents (Claude Code with Chrome, Copilot agent, Cursor)
  ever surface `ReportingObserver` deprecation reports or Issues-panel
  entries, and whether exposing them changes outcomes.
- **Unknown dictionary members.** Measure how often agents misspell option
  members (`addEventListener`, `fetch`, `IntersectionObserver`), and
  consider whether browsers should warn in the console for unknown members
  in dev mode.
- **Deprecation propagation on the web.** A Wang-style study on real old
  pages: does an agent editing a page that uses `document.write` or sync XHR
  extend those patterns?
- **Agent-readable error-message design.** Are web console messages
  specific enough (which element, which value, what to use instead)?
  Compare repair rates for the current messages against rewritten ones.
- **Re-run older studies with 2026 agents.** Re-run CloudAPIBench and Wang
  et al. with current frontier agents that have docs access (for example
  the MDN MCP server) to see how much of the gap remains.
